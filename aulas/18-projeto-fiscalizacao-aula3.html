Objetivos desta aula

  • Entender o modelo publish/subscribe do MQTT (broker, tópico, publisher, subscriber)
  • Subir um broker MQTT (Mosquitto) no nó, como mais um serviço em Docker Compose
  • Criar uma rede Docker compartilhada, pra broker e Node-RED se enxergarem pelo nome
  • Testar publicação e assinatura de tópicos direto no editor do Node-RED

Retomada rápida: nas duas aulas anteriores os grupos prepararam o nó (Docker, grupo docker sem sudo) e subiram Portainer + Node-RED, cada um isolado na própria pasta/rede. Hoje entra o terceiro serviço — o broker MQTT — e, pela primeira vez, dois containers precisam conversar entre si diretamente, não só expor porta pro navegador.

Por que MQTT

  • Protocolo leve, pensado pra dispositivos com pouca CPU/memória e rede instável — o cenário típico de IoT
  • Quem envia uma mensagem (publisher) não fala direto com quem recebe (subscriber) — os dois só conversam com um intermediário
  • Esse intermediário é o broker: recebe tudo que é publicado e distribui pra quem assinou aquele assunto
  • Vai ser o “correio” entre o ESP32 (sensor de velocidade, mais pra frente no projeto) e o microsserviço que compara com o limite da via

Tópico: o “endereço” da mensagem

  • Cada mensagem MQTT é publicada em um tópico — uma string hierárquica separada por /
  • Exemplo: fiscalizacao/carro/velocidade
  • Um subscriber pode assinar um tópico exato, ou usar coringas:
    • + substitui um nível: fiscalizacao/+/velocidade
    • # substitui todos os níveis restantes: fiscalizacao/#

Nota

Convenção do projeto (já usada desde a Aula 1): cada grupo publica no tópico fiscalizacao/<veiculo>/velocidade, trocando <veiculo> pelo nome usado na ficha e nos containers do grupo (ex.: carro, moto).

Roteiro prático — pasta do broker

mkdir -p ~/fiscalizacao/mqtt/config
cd ~/fiscalizacao/mqtt

Assim como Portainer e Node-RED, o Mosquitto também fica isolado na própria pasta, com seu próprio docker-compose.yml.

mosquitto.conf

nano config/mosquitto.conf — colar o conteúdo abaixo, salvar com Ctrl+O, Enter e sair com Ctrl+X:

listener 1883
allow_anonymous true
persistence true
persistence_location /mosquitto/data/
log_dest file /mosquitto/log/mosquitto.log

Nota

allow_anonymous true libera conexão sem usuário/senha — só faz sentido porque o broker fica na rede local da sala, atrás do nó. Num broker exposto na internet isso seria uma falha grave de segurança.

Roteiro prático — rede compartilhada

Até agora cada serviço tinha sua própria rede Docker isolada — funcionava porque bastava expor a porta pro navegador. Hoje o Node-RED precisa falar direto com o broker, então os dois vão entrar numa rede compartilhada, criada uma única vez:

docker network create fiscalizacao

docker-compose.yml — mosquitto

nano docker-compose.yml (dentro de ~/fiscalizacao/mqtt) — colar o conteúdo abaixo, salvar com Ctrl+O, Enter e sair com Ctrl+X:

services:
  mosquitto:
    image: eclipse-mosquitto:latest
    container_name: mosquitto
    restart: always
    ports:
      - "1883:1883"
    volumes:
      - ./config:/mosquitto/config
      - mosquitto_data:/mosquitto/data
      - mosquitto_log:/mosquitto/log
    networks:
      - fiscalizacao

volumes:
  mosquitto_data:
  mosquitto_log:

networks:
  fiscalizacao:
    external: true

Roteiro prático — subindo o broker

cd ~/fiscalizacao/mqtt
docker compose up -d
docker ps --filter name=mosquitto

Conferir se o broker está aceitando conexões:

docker logs mosquitto --tail 20

Nota

Procurem uma linha parecida com Opening ipv4 listen socket on port 1883 no final do log — é o sinal de que o broker subiu certo.

Roteiro prático — reconectando o node-red na rede

O docker-compose.yml do Node-RED (criado na Etapa 02) ainda está na rede isolada dele. Editem ~/fiscalizacao/node-red/docker-compose.yml acrescentando a mesma seção networks do mosquitto — conteúdo completo no próximo slide.

docker-compose.yml — node-red atualizado

services:
  node-red:
    image: nodered/node-red:latest
    container_name: node-red
    restart: always
    ports:
      - "1880:1880"
    volumes:
      - node_red_data:/data
    networks:
      - fiscalizacao

volumes:
  node_red_data:

networks:
  fiscalizacao:
    external: true

Roteiro prático — aplicando a mudança no node-red

cd ~/fiscalizacao/node-red
docker compose up -d

Nota

Não precisa apagar nada: docker compose up -d de novo recria o container do Node-RED já na rede fiscalizacao, e os dados salvos no volume node_red_data (seus flows) continuam intactos.

Node-RED — montando o teste (assinando o tópico)

No editor (http://rpi-10X:1880):

  1. Arrastem um nó mqtt in pro canvas
  2. Configurem o servidor: Server mosquitto, Port 1883
  3. Topic: fiscalizacao/<veiculo>/velocidade (troquem pelo veículo do grupo)
  4. Liguem a saída a um nó debug e cliquem Deploy

Node-RED — montando o teste (publicando)

  1. Arrastem um nó inject (payload texto simples, ex.: 42)
  2. Arrastem um nó mqtt out, mesmo servidor mosquitto, mesmo Topic do slide anterior
  3. Liguem inject → mqtt out e cliquem Deploy de novo

Roteiro prático — testando de ponta a ponta

  1. Cliquem no quadradinho à esquerda do nó inject pra disparar
  2. Abram a aba debug (ícone de inseto, no canto direito)
  3. A mensagem publicada deve aparecer ali — prova que inject → mqtt out → broker → mqtt in → debug funcionou de ponta a ponta

Nota

Nada aparece no debug? Confiram três coisas: o tópico do mqtt in é exatamente igual ao do mqtt out (aqui não vale coringa dos dois lados), os dois nós de servidor apontam pro mesmo mosquitto, e o container do broker está Up (docker ps).

Salvando o trabalho no repositório do grupo

  • Commitem o docker-compose.yml e o mosquitto.conf (pasta mqtt/) e o docker-compose.yml atualizado do node-red/
  • O flow criado no Node-RED (inject → mqtt out → mqtt in → debug) fica salvo no volume node_red_data, mas vale exportar ele também (menu → Export) e commitar no repositório, pra não depender só do container
